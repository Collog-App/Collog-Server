# 파이프라인별 테스트 데이터 계획

목적: [파이프라인 점검](pipeline-audit.md)에서 찾은 계산 문제, 실패 전파, 미활용 정보를 단계별로 검증한다. **정답을 직접 만든 테스트와 생성 모델이 만든 예시를 구분**한다. 이 문서는 계획이며 외부 음성 생성이나 유료 API 호출을 실행하지 않았다.

## 1. 데이터 종류에 따라 검증할 수 있는 것

| 데이터 | 만들 방법 | 확인 가능한 것 | 이것만으로 확인할 수 없는 것 |
|---|---|---|---|
| 단어·시간 JSON | start/end/confidence를 직접 지정 | 휴지·속도 계산식, 경계값, confidence 필터 영향 | STT가 실제 소리의 시간을 정확히 잡는지 |
| 대화 JSON과 정답 facts | 질문·답변·정정·대상자를 직접 작성 | 내용 추출과 grounding, 근거 ID, 질문–답변 연결 | 실제 발음·사투리·잡음의 STT 오류 |
| 결정적 WAV | 코드로 무음·정현파·클리핑·잡음 생성 | 디코딩, 품질 gate, 알려진 pitch의 수치 반응 | 실제 사람의 기침/목소리 탐지 정확도 |
| 대본 기반 TTS | 부모/자녀 발화를 각각 생성 | 합성 음성의 STT→추출 연결, 모델/서버 입출력 | 고령 사용자 실제 통화의 대표성, 질환 변화 |
| TTS + 알려진 시간 편집 | 발화 clip 사이에 정확한 무음 삽입, gain/배경음 변경 | 제어한 조건 변경에 대한 민감도, 시간축/구간 처리 | 편집한 “느린 말”이 실제 건강 변화를 뜻하는지 |
| Suno 등 생성 오디오 | 말소리·음악 등이 섞인 생성 결과를 청취 후 라벨링 | 배경음에 대한 강건성, 오탐 후보 탐색, 예외 입력 | 프롬프트의 기침 횟수·무음 길이·pitch를 실제 정답으로 간주하는 것 |
| 사람이 읽은 대본/연기 녹음 | 여러 화자·기기로 같은 대본 녹음 | 실제 마이크·발음·통화 경로 문제, 명확한 발언의 추출 | 연기한 증상으로 실제 환자/자연 통화 성능을 보장하는 것 |
| 동의된 자연 통화와 사람 라벨 | 실제 사용 조건에서 녹음·검토 | 실제 사용자 환경에서 누락·오탐·측정 불가 비율 | 충분한 표본 없이 전체 사용자 성능이나 건강 상태를 일반화하는 것 |

## 2. Suno의 적절한 역할

공식 발표에 따르면 Suno는 Speech(beta)에서 말소리와 배경 음악을 함께 생성한다. 따라서 생성된 혼합 오디오를 배경음·음악·말소리가 들어간 도전 사례로 사용해 보는 것은 가능하다. 다만 깨끗한 통화 음성의 정밀 기준 데이터로 적합하다는 뜻은 아니다. [Suno 공식 발표](https://suno.com/release-notes/introducing-speech-beta)

권장 실험 용도:

- 음악만 있거나 음악이 섞인 입력에서 STT가 말을 만들어 내는지, F0가 배경 소리를 따라가는지 확인.
- 실제로 들어 보고 라벨을 붙인 기침 비슷한 소리·웃음·목 가다듬기에서 오탐 후보 탐색.
- 같은 음원 파일을 고정해 코드 변경 전후 결과를 비교. 매번 새로 생성하면 모델 변화와 입력 변화가 섞인다.

제한:

- “기침 세 번”, “2초 침묵”이라고 요청해도 실제 출력이 그 조건이라는 보장은 없다. 생성 결과를 확인한 뒤 라벨링한다.
- 음악이 없는 말소리 생성 여부, 기침의 사실성, 정확한 구간 제어는 이번 확인에서 검증하지 않았다.
- 생성된 기침을 사람이 기침처럼 들린다고 판단해도 실제 기침 데이터의 대체 정답으로 취급하지 않는다.
- 원하는 결과가 나올 때까지 생성한 파일만 모으면 쉬운 사례로 편향될 수 있다. 실패 생성물과 선택 기준도 기록한다.

대본을 그대로 읽는 입력이 목적이라면 우선 기존 ElevenLabs 경로를 재사용하는 편이 작업량이 적다. ElevenLabs에는 문자별 시간 정렬을 반환하는 API도 있다. 단, provider alignment도 독립적인 사람 라벨은 아니므로 정확한 무음 길이는 후처리로 직접 넣고 검증하는 쪽이 명확하다. [공식 timing API](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps)

| 파일 | 사용할 부분 | 주의할 부분 |

| [extraction_cases.json](../evals/extraction_cases.json), [evaluate_extraction.py](../scripts/evaluate_extraction.py) | 더미 대화와 추출 평가 흐름 | mock은 실제 Gemini 품질 검증이 아님 |
| [seed_mock_history.py](../scripts/seed_mock_history.py) | ElevenLabs로 부모/자녀 WAV 생성, 주차별 replay | API 비용 및 DB 쓰기 발생. 양 화자 대본을 별도 파일로 읽으므로 자연스러운 교대 대화 시간축이 자동 구성되는 것은 아님 |
| [replay_call.py](../scripts/replay_call.py) | 파일을 실제 분석 경로에 투입 | 외부 provider 및 DB/스토리지 영향. 분리된 분석용 환경에서 실행 |
| [seed_narrative_history.py](../scripts/seed_narrative_history.py) | 화면/집계용 이력 데이터 구성 | 원본 음성 분석 성능을 검증하는 경로와 구분 |

`seed_mock_history.py`의 “안정/악화” 대본 구분은 대화 내용 시나리오다. “기침이 늘었다”는 말을 TTS로 읽는 것과 실제 기침 소리가 늘어나는 것은 다르다. 이 대본만으로 음향 지표의 기대 방향을 정하면 안 된다. 또한 파일 길이가 20초 이상이라고 STT 단어 발음 시간 합도 20초 이상인 것은 아니다.

## 4. 첫 번째 테스트 묶음 제안

처음부터 전부 end-to-end로 실행하지 않고 입력 지점을 나눈다. 앞 단계 실패가 뒷 단계 검증을 막지 않도록 하기 위함이다.

### A. 단어 시간 계산 — 외부 API 없이 실행

- gap `299/300/2000/2001ms`: 경계 포함 여부.
- 같은 3초 gap을 한 segment 내부/두 segment 사이에 배치.
- 중간 단어 confidence `0.49/0.50/None`: 삭제가 휴지에 미치는 영향.
- 겹친 단어, 빈 words, 숫자/영어 포함 텍스트.
- 부모 발화 길이 `19.4/19.6/20.0초`: pipeline과 analyzer 판정 비교.

현재 코드에 맞는 예상값과 제품에서 원하는 동작을 별도 컬럼으로 둔다. 기존 동작이 재현됐다고 제품 의미가 적절하다는 뜻은 아니다.

### B. 파형과 품질 — 결정적 WAV

- 동일한 150Hz 톤의 정상 레벨/저레벨/클리핑 버전.
- 길이 4.9초와 5.1초, 허용 sample rate별 동일 신호.
- 구간별 F0가 알려진 톤과 무음의 조합.
- 정상 WAV와 잘못된 header/선언 sample rate 불일치.
- 모델 없음/체크섬 불일치/모델 예외 주입.

정현파는 알고리즘 sanity check다. 음성의 voiced detection 정확도로 해석하지 않는다. 품질 경계는 PCM 양자화 영향을 고려한 허용 오차를 정한다.

### C. 소리와 내용의 교차 사례

| 음성 내용 | 실제 이벤트 | 기대하는 분리 |
|---|---|---|
| “기침 안 했어” | 기침 소리 없음 | 내용은 부정 진술, 음향 이벤트는 별도 결과 |
| “요즘 기침해” | 기침 소리 없음 | 증상 언급을 음향 기침으로 세지 않음 |
| 건강 언급 없음 | 라벨된 기침 소리 삽입 | 내용 없음과 음향 이벤트를 독립 처리 |
| “어제는 잘 잤어” | 웃음·목 가다듬기 삽입 | 기침 hard negative 확인 |
| 짧고 구체적인 건강 발언 | 긴 무음 또는 잡음 | 내용의 근거 충분성과 음향 충분성을 구분 |

실제 기침 양성 평가에는 권한이 있는 실제 녹음과 사람이 확인한 구간 라벨을 사용한다. 생성 소리는 별도 synthetic subset으로 평가한다. 기본 `cough_detector_validated=False`에서 외부 출력은 계속 측정 불가인 것도 따로 검증한다.

### D. 교대 대화와 실제 장치

부모·자녀 발화를 clip 단위로 만들고 공통 timeline에 배치한다. 두 track 모두 같은 시작점을 가진 파일로 만들어 질문 후 0.5/1/3초 응답, 겹쳐 말하기 등을 구성한다. 각 트랙 첫 발화 전 무음을 제거하면 정답 시간축이 깨진다.

그다음 같은 대본을 실제 iPhone 통화로 녹음해 raw/Egress 시작점 차이, 업로드, 전사 timing을 확인한다. 파일 replay는 LiveKit 캡처·네트워크·기기 오디오 처리를 재현하지 않는다.

## 5. 정답 및 결과 저장

```text
manifest.csv
case_id,base_case_id,split,input_kind,source,generator_version,seed,
audio_sha256,speaker_id,transform,expected_stage,expected_status,label_origin

annotations.csv
case_id,track_id,event_type,start_ms,end_ms,annotation_status

results.csv
case_id,stage,metric,expected_value,actual_value,status,reason,
absolute_error,algorithm_version
```

- 생성기 설정과 원본 파일 hash를 고정한다. seed만으로 완전 재현을 가정하지 않는다.
- 알려진 무음 삽입 구간과 사람 판단의 발성/기침 구간은 `label_origin`으로 구분한다.
- 같은 원본에서 만든 잡음·볼륨 변형은 같은 split에 넣는다. 정답 확인용 holdout에 변형본이 새지 않게 한다.
- 기침은 현재 모델의 병합 “구간” 정의에 맞춰 평가하며, 개별 기침 횟수와 섞지 않는다.
- 수치 오차, 내용 누락/오탐, 측정 불가 비율, 단계별 실패율을 따로 보고한다. 서로 다른 종류의 실패를 하나의 정확도 수치로 합치지 않는다.

## 6. 시작 순서

1. API 없이 A/B의 계산·예외 fixture로 현 동작을 고정한다.
2. 소수의 대본 TTS를 만들고 실제 출력 파일을 확인한 뒤, 정확한 무음·잡음 변형을 적용한다.
3. Suno 입력은 별도 도전 사례 묶음으로 추가한다.
4. 실제 기기 녹음과 자연 통화 holdout으로 적용 가능성을 확인한다.

이렇게 하면 합성 데이터로 **만들 수 있는 조건**과 합성 데이터만으로 **주장할 수 없는 성능**이 구분된다.
